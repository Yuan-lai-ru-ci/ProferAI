# 任务图重审：宿主无关的工作事实视图

> 日期：2026-11-15（GMT+8）
> 状态：**产品定位与解耦方向已确认；本文的详细模型、接口与迁移建议待评审，未实施。**
> 源码基线：`be2de2bb`，主仓库存在并行 WIP；本文描述的是本轮读取的工作树，不等于对应提交的完整内容。
> 范围：设计、事实核验、迁移边界与验收建议。不修改产品代码，不新增自动推进，不启动开发环境，不提交或发布。

## 1. 结论与已确认方向

任务图定位从“Agent 主动维护的一张计划 DAG”，调整为 **工作演进的事实视图**。核心回答：解决什么问题、做过哪些尝试、哪些已失败或被替代、结果凭什么成立、当前卡在哪里。

用户在本会话已确认：

1. 以执行事实追踪（C）为核心，而非统一接管用户计划、调度与执行。
2. 工作事实不以画成图为目标；简单工作可以是列表或进度链，出现真实分支时再展开。
3. 采用主线、尝试分支、证据与产物的方向；失败/放弃/替代不应被最终成功状态覆盖。
4. 遵守 Profer 的 Electron 解耦原则：事实独立存在，Electron 是宿主与消费端之一。

本文进一步建议的默认值：失败与被替代的尝试保留、折叠展示；不再为连图而推断依赖；不新建第三套可写 Task/Run 状态；先统一事实投影，再调整体验。这些细节是设计提案，不扩大为已获准的施工范围。

### 目标

- 可信：区分观测、声明与推断；从事实可追到原始来源。
- 可恢复：实时显示、重启恢复与不同端查询遵循同一套重放规则。
- 可解释：一次失败不等于目标失败；一次运行结束不等于用户目标达成。
- 可脱离桌面：无需 Electron、React 或 Provider SDK 即可重建和查询事实。
- 可渐进：复用 `project-core`、Fabric 与 Run Ledger 的既有边界，保留旧数据与权限防线。

### 非目标

- 不以本项目重做 Goal、Planning 或通用工作流/调度引擎。
- 不自动续跑、重试或取消传播；读取事实、依赖边或恢复账本不会授予执行权限。
- 不采集模型隐式思考；只记录可见行为、显式声明和可引用的结果。
- 不将每个 read/grep/工具调用升格为任务节点，不默认使用额外 LLM 回溯整段对话。
- 不新增数据库、跨设备多写者合并协议或新包；不把所有产品业务塞进 Agent Runtime。
- 首版不要求 Pocket 和正式 CLI 都上线，但必须有非 Electron 的实际消费验证。

### 对前述讨论的校正

- renderer 的旧事件转换器不能直接认定仍参与生产写图；当前能确认的是实时 TaskItem overlay 仍在生效。
- 不应直接把项目 TaskNode 与 Fabric AgentTask 合并：来源和粒度不同，很多图任务根本没有 Fabric AgentTask。
- Pi Harness 的 `goalId`、用户 Goal 与业务 Task 不是同一身份；例如消息中的 `graph_focus.goal` 不能直接当作用户确认的持续目标。

## 3. 推荐方案与备选

**推荐：在现有 project-core 内建设只读工作事实投影，宿主适配既有 Task/Run/Harness 来源。**

- 优点：复用真实执行账本，不要求开启 Fabric 服务；可边界测试；先恢复可信度，再改展示。
- 代价：过渡期需保留旧图适配和缺失关联诊断，不能一次消灭所有模型差异。

备选：先将所有图任务、桌面对话和委派统一迁入 Fabric 再做视图。长期有统一命令模型的收益，但当前 Fabric 终态、重试、独立来源和依赖执行尚有未闭合边界，会把小范围重审扩大为执行链迁移。不推荐作为前置条件。

只改画布/增加连线样式不作为可取备选：无法解决身份、证据和恢复不一致。

## 4. 概念与状态所有权

### 4.1 三个主要展示对象

| 对象 | 回答的问题 | 权威来源与约束 |
|---|---|---|
| 工作单元视图 | 要解决什么，结果是否已被声明/接受 | 已有 AgentTask 的 TaskView，或旧图 TaskNode 的兼容投影；不是新增可写实体 |
| 执行尝试视图 | 在何处、用什么执行上下文做过什么 | 引用 AgentRun 与可定位的工具/turn 事实；不拥有新的 Run 状态机 |
| 证据/产物引用 | 某结论或结果由什么支持，是否仍适用 | 具体工具结果、验证记录、消息/文件修订引用；路径不等于访问授权 |

Goal 是可选的上层目标引用，不为图强造 Goal。Session 是执行上下文与转录容器，不拥有工作完成真值。Delegation 是执行关系和生命周期协调，不等同于 TaskView 或 Session。

### 4.2 不把“尝试”简单等同于一次 Run

- Run 是逻辑执行生命周期；同一个 Run 内可能先试 A 后换 B，同一工作也可能跨多个 Run 继续。
- 尝试默认从已存在的 Run 投影；只有出现显式方案边界才拆为多个片段。
- 片段必须引用稳定锚点（Run ID + 事件/工具调用 ID 范围）；不能以段落摘要、标题相似或墙钟时间猜测。
- 新策略在后续 Run 继续时，用显式延续关系组合；底层的每个 Run 仍独立可查。
- Run 等待输入后 resume、runtime handoff、网络层重试均不自动生成“新方案”。
- 尝试的运行结果（失败/停止/完成）和语义处置（继续采用/放弃/被替代）分开；成功执行也可能产出后来弃用的结果。
- **Run 生命周期只属于 Run，不直接赋给片段。** A/B 同属一个 completed Run，不代表 A 和 B 都成功；片段 outcome 只能来自有来源的显式声明或类型化观测，否则为 unknown，并单独显示所属 Run 状态。
- 声明“A 失败”、结构化验证失败、被 B 替代是三个可分别查询的事实；跨 Run 组合也不产生新的可写运行生命周期。

“Attempt”在首版是带来源锚点的只读投影/注记，不增加独立可写生命周期。需要新方案标签时新增显式注记，不改写历史 Run。

### 4.3 四个维度，不合成一个绿色状态

1. **工作结果**：沿用来源状态，并显示来源是执行命令、Agent 声明还是用户接受。
2. **执行状态**：只读 Run Ledger；stopped/failed 不自动取消工作目标。
3. **验证状态**：引用验证记录，按标准、修订与证据范围计算；未知不等于通过。
4. **阻塞信息**：明确是执行等待、声明的前置未满足，还是来源不完整；依赖未满足不等于运行时已经强制禁止执行。

现有 `TaskView.completed` 仍是兼容协议投影，不能因此显示“用户目标已验证达成”。首版保留原字段，同时独立呈现声明/证据；如要改变权威完成命令，另做契约变更，不在 reducer 偷改。

### 4.4 身份与关联

- 内核使用带命名域的 EntityRef（概念名），例如来源种类 + 所属会话/账本 + 实体 ID；不能仅用字符串 `taskId` 跨来源 join。
- 图节点、Fabric Task、Delegation、Run、Harness turn/goal 保持类型区分。
- 同一实体仅在宿主提供可靠映射时合并展示；`delegation:<id>` 与 delegationId 可通过已核实映射关联，不靠前缀猜所有业务身份。
- 一个父 Run 内可有多个图工作单元：需要工作↔Run/工具片段 binding，不能把 Run.taskId 当作所有子工作的唯一归属。
- 同一工作多会话执行保留关联列表，不再用一个 sdkSessionId 覆盖旧关联。
- 无映射时保留独立条目或“未归属执行”；允许图为空，不为了好看制造根节点。

既有 `ResourceRef` 暂无 artifact/verification/attempt 类型，不能声称直接复用全部引用类型。优先复用其已有 task/run/session/message 引用；证据和片段使用领域专用判别联合引用，如需扩展公共协议，独立评审版本兼容。

## 5. 关系语义：不能全部塞进 dependsOn

首版建议仅保留以下少量关系/附属记录：

| 关系 | 精确定义 | 来源 |
|---|---|---|
| dependency | A 声明依赖 B 的结果；方向固定为 A→B | 用户/Agent 显式声明或已有契约字段 |
| subtask/delegation | 属于父工作或由某次执行委派；两者分别保留类型 | 明确 parentTaskId、委派记录或结构化绑定 |
| attempt-of | 执行/片段在处理哪一个工作 | 宿主 Run/片段绑定或显式注记 |
| supersedes | 新尝试/结果取代旧尝试/结果，并保留理由 | 用户/Agent 显式声明，附来源消息/事件 |
| evidence attachment | 某个有范围的证据支持或反驳哪个结果/标准 | 可定位的验证/工具记录或注明为声明的引用 |

时间顺序只用于排序，不能推断上述关系。并行来自运行时间区间重叠/可信运行事件，不因两个节点并列就宣称真实并发。`forkFrom` 旧数据只按“旧分叉关联”兼容，不自动解释成“方案 B 替代 A”。

每条关系/注记必须标明 `observed`（宿主观测）、`declared`（用户/Agent 声明）或 `legacy_unspecified`（历史来源不详），并能指回来源。推断候选不进入权威 dependency/替代关系，也不影响权限、调度和完成状态。

明确依赖需校验自环/循环与引用范围；遗留坏边可读、给诊断，不用丢节点掩盖问题。关系可被更正/撤回，保留旧来源，不覆盖成“从来没有发生”。

每条 binding/关系/注记有稳定 record ID；更正或撤回必须引用被修订记录。同流按来源 sequence 处理，跨流无因果冲突同时保留并诊断，禁止“最后到达者覆盖”。实体后到时重新解析已有悬挂引用；领域记录和 diagnostics 均采用确定性排序，不因跨流交错顺序变化。

## 6. 事实采集与 Agent 的最小责任

运行时自动提供：Run/Trigger 身份、开始/等待/终止、工具结果与结构化退出状态、委派身份和可确认的产物变化。Provider 差异在适配层消化；未知工具只记 opaque 事实，不推断验证通过。

Agent 只补运行时无法知道的语义：某片段在处理哪个工作、为何改变方案、哪个新结果替代旧结果、工作完成声明及其标准/证据引用。保留现有 create/update 工具作为兼容入口，是否新增专用结构化动作在契约阶段决定；不要同时重开 Todo、Task 和 Work 三套可写工具。

失败工具不等于整个尝试失败，更不等于工作失败；一次测试失败可以只是故障定位证据。没有明确归属时挂在 Run 明细里，不全部挂到“最近焦点任务”。

不要求每轮为图额外汇报、不为填充图而强迫模型造任务。语义标注失败不改变底层工具结果；但工作记录必须暴露“不完整/未关联”诊断，不能悄悄显示成功。

## 7. 事件、恢复与存储

### 7.1 有来源的事实信封

在既有事件源之上建立可验证的归一入口，不复制整段消息、命令输出或凭据。建议字段：schemaVersion、eventId、sourceRef/sourceEventId、streamId/sequence、occurredAt、recordedAt、相关实体引用和结构化 payload；ID、时钟与 I/O 由宿主注入。

- 单流由一个写入所有者分配递增 sequence，reducer 不依赖 `Date.now()` 产生业务状态。
- 多流只保证各自顺序；组合快照携带来源游标集合。跨流因果来自显式引用，不是按墙钟时间全局排序。
- 同一源事件在重投/重启时映射到同一 eventId；不得每次消费生成新的随机事实 ID。
- 去重作用域是来源命名域+事件 ID；来源损坏或字段冲突要诊断，不把两个不同事件静默合并。
- 全量重放与增量 apply 必须得到相同的领域快照；空图时间不靠当前时钟漂移。
- “已记录”“已解释为归属”“已验证”分别表述，不能因成功入账就升级结论。

### 7.2 先落盘，再发布；不制造双写事务假象

Run Ledger 与现有图/Harness 并非一个原子事务，不声称把两次文件写入拼起来就是一致。

1. 原执行系统保有自身生命周期和写入责任；工作投影从已提交来源事件重放/对账。
2. 投影可重建，保存消费游标与来源引用，断电后从游标续读；对重复投递幂等。**来源采集检查点**与**消费者订阅游标**不是同一对象：前者是每个来源已可靠消费的位置，后者属于已发布投影的 epoch/revision。
3. 快照与来源采集检查点要么同一提交保存，要么允许重复读取安全重建；不得推进检查点却丢弃尚未提交的事实。只有成功持久化的事实才以 committed revision 对消费者发布。流式临时提示如需保留，必须显式标为 provisional，不能参与完成/依赖真值。
4. 消费者读取 snapshot + 绑定 projection/schema epoch 的 cursor，再订阅 cursor 之后可重放的事件；不能仅连接实时监听。订阅断档、epoch/版本不匹配时重新取快照，而不是在 UI 合并两套解释。
5. 投影写入失败不把已执行副作用回滚或重跑；显示记录滞后/不完整并可对账。未可靠入账的语义命令不能返回“已保存成功”。
6. 新增的纯语义注记只有一个持久化所有者；UI 发送领域命令，不发送任意 GraphEvent。记录来源必须由宿主上下文产生，模型不能自填身份或授权。

现有来源并非都已满足提交合同：Fabric 文件事件日志在落盘异常时打印错误后仍返回内存事件（`apps/electron/src/main/lib/agent-fabric/fabric-store.ts:156–166`）。因此收到回调不代表已提交；G2 必须按来源选择落盘回读确认或 provisional 降级，不能直接给全部旧回调盖 committed 标记。

文件层继续采用本地 JSON/JSONL 与 Node-only adapter，不新增数据库。优先利用 session-store 的路径与存储能力；增量扩展要保留图服务当前的安全路径/symlink 校验，不能仅换读写函数就失去防护。首版按单宿主写入，跨进程写者应有显式排他/冲突策略，尚不做多设备共同写账。

### 7.3 损坏、未知与恢复

- 损坏 JSONL 行、未知版本、悬挂引用可跳过/隔离并返回 diagnostics；不能全图清空，也不能默默忽略成“没有问题”。
- 不认识的新事件保持只读兼容并报告语义不完整，不输出完整性保证。
- 重启后先由 Run 的宿主做接管/中断对账；事实内核只展示结果，不自发启动查询或工具。
- Fork/rewind 以稳定消息/事件锚点与来源游标切边界。当前按 timestamp 复制可兼容，但不能成为新跨流因果标准；旧数据边界不精确要注明，不篡改原记录。
- 已取消/放弃、已被替代的条目保留并默认折叠。隐藏/纠错是呈现与附加记录；真正数据删除仍走用户授权与数据保留政策，日志不是“永不允许删除”的理由。

## 8. 模块归属与宿主边界

```text
已有执行源（Fabric Task / Run Ledger / 工具结果 / 委派 / Harness）
                         │ 明确身份、事件与来源适配
                         ▼
         project-core 工作事实归一 / reducer / 查询
                         │ 同一快照与增量语义
              ┌──────────┼──────────┐
              ▼          ▼          ▼
        Electron UI   Node 查询端   其他客户端适配
```

这不是把 Task/Run/Harness 数据都搬到一个包里。最小分工如下：

| 所有者 | 输入 → 产出 | 边界与验证证据 |
|---|---|---|
| `agent-fabric` | AgentTask/来源策略 → TaskView 与权威命令结果 | 不导入 project-core 或 UI；不为显示复活终态 |
| `agent-runtime` | Run/Trigger 生命周期 → 执行事件与快照 | 不拥有业务图、布局或桌面 IPC；沿用 Run Ledger 测试 |
| `project-core` | 已归一的记录与显式 binding → 事实快照、关系、诊断、摘要 | 禁止导入 Electron/React/SDK/磁盘；同一 reducer 做增量与恢复 |
| `session-store` / 宿主存储 | 路径、事件与游标 → 可靠持久化/读取 | Node 子入口；路径授权、故障注入、原子性与并发策略测试 |
| 可独立测试的 source adapter | 标准 Run/工具/委派来源 → 归一事实 | 优先复用 Provider/runtime 已给出的标准事实；格式兼容不进入 reducer，归一函数可脱离 main 测试 |
| Electron main / 产品 host adapter | 可信上下文与用户命令 → 来源装配、权限校验、I/O 与领域响应 | 装配 source adapter，不在 main 再解析一套 Provider 真值；其他宿主可注入相同归一逻辑 |
| preload / IPC | 领域命令、snapshot/cursor、订阅 → 类型化传输 | 不自带状态机；sender/session 校验；注册链变更需单独放行 |
| Renderer/domain | 已提交快照与增量 → Jotai 状态、筛选、布局、导航 | API 边界隔离 window.electronAPI；不再从 toolActivities 推导权威边 |
| 非 Electron 消费端 | 同一事件夹具/存储 adapter → 可查询摘要与明细 | 不通过桌面 IPC；不要求安装 Provider SDK，不启动 Electron |

接口概念限制在四类：读取快照、按游标订阅、提交少量语义命令、解析受控引用。具体函数名/TypeScript schema 后置，不在现有调用图尚未封口前扩大 RuntimePorts。

已有 `minimal-pi-host` 是内存执行替身，明确不含协作等产品能力（`packages/agent-provider-pi/src/host/minimal-pi-host.ts:1–11`）。它不能代替“真实文件持久化的第二宿主”验收；新视图可先通过独立 Node 文件消费端证明不依赖 Electron，完整执行链的双宿主生命周期验收仍是另外一项工作。**读端宿主无关、来源采集归一可复用、完整执行链宿主无关**是三个不同验收结论，不以第一个替代后两者。

## 9. 用户体验与产品验收

默认入口建议称“工作记录/工作进展”，不急于全局改名。内部和旧 API 可继续沿用 graph 名字，避免将重命名与结构迁移绑成一刀。

### 默认摘要回答五个问题

1. 当前在解决什么？
2. 最近取得了什么结果？
3. 有什么证据，适用于哪个版本？
4. 卡在哪里，阻塞来自什么？
5. 下一步是建议还是已经执行？

### 按真实复杂度展开

- 简单：列表/紧凑进度链。无依赖时只是按时间排列，不画虚假箭头。
- 尝试：一个工作下折叠列出 A 失败、B 替代 A、对应证据。尝试只增加历史，不增加“待办总数”。
- 并行：按真实执行来源/委派展开泳道；独立工作保持独立，不强挂成子任务。
- 关系复杂：用户主动打开图视图，图是相同事实的可选布局。

不默认用“已完成节点/全部节点”表示目标完成百分比，避免探索越多、看起来越退步。可显示“已声明完成的工作数、活动执行数、失败尝试数、待验证结果数”，各自命名且不混算。

证据卡片显示观测/声明、结果、范围、发生时间、来源和可用性。文件若已改变或证据缺少修订信息，标为过期/适用性未知，不沿用旧绿色“已验证”。回合结束只显示“本轮结束”。已替代条目保留失败原因和证据，默认折叠但可一次展开。

“继续执行”不是读视图的默认能力：若保留已有手动入口，仍经原授权/运行准入路径；UI 点击、查询图、选择节点均不得隐式授权自动执行。

## 10. 迁移建议：一阶段一边界，不同时推倒

本节是建议顺序，不是已批准排期或自动执行计划。首轮施工放行范围建议仅 G0/G1；其余要在对应门槛满足后单独确认。

### G0：身份与行为合同冻结（无产品行为变更）

- 把现有项目 TaskNode、Fabric Task、Delegation、Run、Harness turn/goal 的对应关系写成夹具与契约。
- 明确图工作↔Run/片段绑定及命名域，覆盖原生 Task ID 在不同会话/运行中可能冲突的情况。
- **阻断项**：定义旧 Fabric 终态的新执行如何关联同一工作。首版不复活旧 Task；新授权执行用新 ID 与显式关联，视图可展示关联但不能暗中拼成稳定工作实体。若需要“一个长期工作、多个可重试命令”的可写模型，另做 Task 协议决策后才宣称支持。
- 审核 Fabric `dependsOn` 的校验与真正调度行为；当前不能从存在纯校验函数推断 Gateway 已执行依赖闸门。
- 输入：本设计和当前源码；产出：冻结的身份/状态/错误合同、旧数据金样；依赖：无；证据：合同用例通过，不改运行行为。

### G1：纯事实投影与只读非桌面消费

- 在 project-core 增加最小 reducer、来源引用、binding、证据与诊断；复用旧 parser 作为 legacy adapter。
- 用独立 Node 入口读取同一批事件夹具及临时文件，验证摘要和明细，不装 SDK、不走 Electron。
- 不新增通用 Work 实体、第三套 Task 状态或大量公共抽象。
- 输入：G0；产出：只读内核/适配夹具；证据：确定性、去重、增量/全量等价、边界扫描和文件往返测试。

### G2：宿主采集与存储接线（单独放行 main/执行边界）

- 用可信 Run/工具/委派来源替换当前焦点启发式；新增关系只接受显式输入。
- 主宿主一个写入所有者；提供 committed revision/cursor；失败可恢复与诊断。
- 先旁路只读对比旧图，不同时写两套权威 Task；新投影可删除重建。
- 输入：G1；产出：宿主适配与存储恢复合同；证据：Claude/Pi 对等夹具、写失败、重启与重复投递验证。
- 退出条件：新来源完整性达标，旧生成器每一条用途有替代或明确保留理由。

### G3：Renderer 统一消费（单独放行 UI/preload/IPC）

- 先保持现有外观消费新投影，移除实时 TaskItem 的权威 overlay；通过后再做列表/尝试折叠/泳道。
- renderer/domain 隔离宿主 API，UI 不负责解释工具回包、补依赖或写通用事件。
- 输入：G2；产出：统一读链路与新体验；证据：组件/订阅合同测试、真实渲染、切会话/重连/重启人工验收。
- 不在本刀顺手改 AgentView、全局侧栏等并行 WIP。

### G4：兼容退场与第二消费端

- 验证旧会话、fork/rewind、来源缺失、实体隐藏及导出，保留回退开关与原文件。
- 无法识别为“显式”的旧依赖保留为 legacy_unspecified，不重写成伪造历史；不能假装从旧数据可靠区分自动边和人工边。
- alias/binding 不删除旧身份，不将回合时间戳当作精确片段边界。
- 再按真实需求接正式 CLI/Pocket；读端缺字段时显示降级，不通过桌面代理伪称独立。
- 兼容 facade 必须记录删除条件，不能以“以后再清理”无限延长。原始用户记录不自动删除/覆盖。

## 11. BDD 验收矩阵（待实现）

以下为建议验收，不代表本轮已执行测试。

| 场景 Given / When | 必须满足的 Then | 责任层 |
|---|---|---|
| 连续创建 A/B，未声明依赖 | 有顺序，无 dependency、无伪分叉；图可以不连通 | core + host |
| A 方案失败，明确改用 B，B 验证通过 | A 失败及证据保留；B supersedes A；工作完成声明与验证各自可查 | core + UI |
| 同一 Run 内先 A 后 B | 有片段锚点才拆两次尝试；片段 outcome 无单独来源则 unknown，不继承整个 Run 终态 | core + host |
| 工作跨两次 Run，前次被停止 | 不覆盖旧 Run；无新授权不自动续跑；停止不取消工作 | runtime + host |
| Run 等待回答后恢复、handoff 或网络重试 | 同一逻辑 Run，不虚增方案尝试 | runtime + core |
| 并行委派/批量委派、独立会话 | 所有可信关联可查，不遗漏 batch；关系和布局不决定取消传播 | host + core |
| 同一来源事件重投，跨会话 ID 恰巧相同 | 同源幂等、不重复节点；异源不串图 | core + store |
| 时间戳相同/倒退、跨流事件先到引用后到实体 | 按流序列与显式引用收敛；有悬挂诊断，不以时间造因果 | core |
| 相同逐流内容以不同跨流交错顺序输入，含冲突与撤回 | 快照及 diagnostics 一致；无因果冲突保留，撤回只作用于被引用记录 | core |
| 来源回调成功但落盘失败、快照/检查点提交中断 | 不发布 committed；恢复不跳过未处理事实；消费者旧 epoch 触发重取 | store + source adapter |
| 实时消费后重启全量读取 | 同游标领域状态一致；无依赖回弹或状态退化 | core + UI |
| snapshot 与 subscribe 之间发生新事件、断线后重连 | 不漏不重；cursor 失效重取快照 | host + UI |
| 旧图有来源不明的自动边或损坏行 | 原始文件不变；legacy 标识和诊断可见，不能伪称显式依赖 | legacy adapter |
| 写入失败/进程退出/并发写冲突 | 不发布未提交 revision，不谎报保存成功，不重跑副作用，可对账 | store + host |
| 工具成功但无退出码/没有匹配验收标准 | 仅标工具调用成功/未知，不标工作已验证 | host + core |
| 测试通过后产物已改、文件已失效 | 证据修订不匹配时过期/未知，不继续作为当前验证通过 | core + resolver |
| Fabric Task failed/expired 后恢复查询 | 旧终态不复活；新尝试需新命令身份和显式关联 | Fabric + runtime |
| 图循环/缺失依赖/blocked 任务 | 明确区分声明阻塞与实际执行等待；内核不代替调度 | core + host |
| fork/rewind 到既定事件边界 | 新分支不携带边界后的事实；原分支不被改写 | store + host |
| 不启动 Electron、不安装 SDK，Node 读文件 | 与纯夹具相同的工作/尝试/证据查询结果；不隐式打开文件或执行工具 | 独立消费端 |
| 注记带任意路径、伪造 actor/授权或跨会话引用 | 宿主拒绝不合法命令；引用不授予文件访问/跨域查询权限 | host + IPC |
| 简单任务、失败分支、多 Agent、缺证据四类可视用例 | 同一事实有适度展示；失败默认折叠但可查；无强制无界画板 | UI + 视觉验收 |

实施时分别记录：定向单测（目录测试用 `bun test --isolate`）、类型检查、包/域边界检查、diff check、Node 文件往返、真实桌面渲染与人工验收。不能用纯单测通过替代“第二宿主可工作”，也不能用截图代替恢复/权限合同。
